# The order matters: five rules for getting things done

From *The Book of Elon* by Eric Jorgenson — a five-step sequence for improving
almost any product, process or organisation.

The steps are unremarkable individually. The **order** is the insight, and most
organisations run it backwards.

## 1. Make the requirements less dumb

If a requirement should not be in the document, remove it before anything else
happens.

This is harder than it sounds in practice. Sit in enough requirements reviews and
you encounter elaborate, confidently-worded specifications that nobody questions —
on the assumption that somebody senior thought it through.

That assumption is usually the problem. Ask who requested each requirement, what
decision it supports, and whether it would exist if the work started today. Anything
not serving the goal comes out now, not later.

## 2. Delete the part or the process

Counterintuitive, because process is supposed to create order.

It does — for work that matters. Process wrapped around something unnecessary does
not streamline anything; it institutionalises the unnecessary thing and generates
more coordination around it.

Delete it outright rather than improving it.

## 3. Simplify and optimise

Only now, once the remaining steps are genuinely required, is it worth making them
better — in technology, in cost, in people.

Optimising before deleting means spending effort on work that should not survive the
previous step.

## 4. Accelerate

With a process that is necessary and efficient, push the throughput.

## 5. Automate — last

This is where most organisations begin, and it is the expensive mistake.

Automating an inefficient process spends significant money and time encoding that
inefficiency, and makes it harder to remove afterwards — because now there is a
system defending it. Automate only once the process is proven, efficient, and
expected to remain stable.

## Why the sequence is the whole idea

Every step removes work that the following steps would otherwise have to carry. Run
it in order and each stage is cheaper than it would have been. Run it backwards —
automate first, question later — and you have built infrastructure around a
requirement nobody should have accepted.

It applies well beyond engineering. The same discipline works on investment
research: identify the few assumptions that actually change the answer, and test
those, rather than extending a checklist because it feels thorough.

*Based on *The Book of Elon* by Eric Jorgenson.*
